---
title: "Scheduling"
description: "Recurring events by time of day and weekday, with a minimum player count."
---

Each event carries its own list of schedules, edited from the schedule screens in `/captureadmin`. A
schedule is a time of day, a set of weekdays and a minimum number of players online.

## What a schedule holds

| Field | Meaning |
|---|---|
| `name` | A label for the entry. Defaults to the event id. |
| `time` | `HH:mm`, the exact minute it fires. Required. |
| `days` | Weekday names, or `*` for every day. An empty list also means every day. |
| `min-players` | Players who must be online for it to fire. Defaults to `0`. |

An event can have as many schedules as you want: three different times on weekdays and one on
Saturday is four entries on the same event.

## How firing works

The scheduler checks once a second. When the current weekday and `HH:mm` match an entry, that entry
fires — once per minute at most, so a check landing twice in the same minute cannot start it twice.

It then skips the start when either is true:

- Fewer players are online than `min-players`.
- That event is already running.

Both cases are written to the console debug log rather than being silent.

<Callout type="note" title="It is not cron">
Despite the internals being called cron entries, there are no cron expressions. A schedule is a
weekday set plus one exact minute; there is no "every 15 minutes" and no interval syntax. Recurring
more often than daily means adding more entries.
</Callout>

## Timezone

Every schedule is read against one clock, set globally:

```yaml title="config.yml"
scheduler:
  timezone: ""
```

Empty means the machine's own timezone. Otherwise it takes a zone id such as `America/New_York` or
`Europe/Madrid`.

<Callout type="warning" title="An invalid zone id stops the scheduler">
The value is parsed at load. Use a real IANA zone id — the ones you would find in `/usr/share/zoneinfo`
— rather than an abbreviation like `CET`.
</Callout>

## Time until the next one

The next fire is computed by walking forward up to seven days from now and taking the earliest
matching entry. That value is what feeds:

- `%exyliacapture_<id>_time_until_start%` for one event.
- `%exyliacapture_next_event_time_until_start%` for the soonest event on the whole server.
- The `SCHEDULED` state a hologram shows when an event is not running but has an upcoming schedule.

An event with no schedules reports nothing rather than zero, which is how a hologram tells "not
running, but coming" apart from "not running at all".

## Starting by hand

A schedule is not required. `/captureadmin start <id>` starts an event immediately, and it obeys the
same rule about not starting one that is already running.
