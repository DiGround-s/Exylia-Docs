## The nodes

| Permission | Default | Grants |
|---|---|---|
| `exyliaarmorskin.admin` | `op` | Every subcommand of `/armorskin`: `give`, `remover`, `list`, `refresh` and `reload`. |
| `exyliaarmorskin.skin.<id>` | — | Applying and wearing that one skin. |
| `exyliaarmorskin.skin.*` | `op` | Every skin. |

Both fixed nodes are declared in `plugin.yml` with `default: op`, so an operator owns every skin out
of the box and everybody else owns none until you say otherwise.

## The per-skin node

There is no `permission` key in `skins.yml`: the node is **derived from the id**, lowercased, so the
skin `galaxy` is always `exyliaarmorskin.skin.galaxy`. Add a skin and its node exists; rename it and
the node renames with it.

```text
/lp group default permission set exyliaarmorskin.skin.blue_vex true
/lp group vip permission set exyliaarmorskin.skin.galaxy true
/lp group mvp permission set exyliaarmorskin.skin.* true
```

## What the node is checked for

<Steps>
  <Step title="Applying">
    Dragging a skin item onto armour without the node is refused with the `no-permission` message.
    Nothing is written and nothing is consumed. Governed by `behaviour.require-permission`.
  </Step>
  <Step title="Wearing">
    A piece whose skin the **wearer** may not use is drawn as the real armour — to them and to
    everyone else — and it plays no effects. The id stays on the item, untouched. Governed by
    `behaviour.hide-without-permission`.
  </Step>
</Steps>

The wearing check runs whenever the piece is reconciled: on equip, on join, on respawn, on
`/armorskin refresh` and on `/armorskin reload`. Revoking a node mid-session therefore takes effect
on the next of those — `/armorskin refresh <player>` makes it immediate. Granting it back and
refreshing brings the skin straight back, because nothing was ever removed from the item.

## The two switches

```yaml title="config.yml"
behaviour:
  require-permission: true
  hide-without-permission: true
```

| Combination | Result |
|---|---|
| Both `true` (default) | A skin is owned: you need the node to apply it and to be seen wearing it. |
| `require-permission: false` | Anybody holding the item can apply it, but a wearer without the node is still shown the real armour. |
| `hide-without-permission: false` | The node is needed to apply, but once applied the skin is shown to everyone forever — a permission that only gates the purchase. |
| Both `false` | Nobody is checked. This is how the plugin behaved before per-skin permissions existed. |

<Callout type="warning" title="Commands and the API are never gated">
`/armorskin give` hands out any skin item to any player, and `apply()` in the API writes any skin
onto any piece, regardless of the node or of `require-permission` — those are the tools you use to
grant a skin. What the wearer lacks the node for is the **display**, which `hide-without-permission`
governs.
</Callout>

## Selling skins

Because a skin travels as an item **and** carries a node, you can sell either half:

| You want | Do |
|---|---|
| A consumable a player buys once | Give the item and grant the node with it. |
| A rank perk | Grant `exyliaarmorskin.skin.galaxy` to the rank; hand the item out freely. |
| A skin anyone may use | Grant its node to `default`, or turn both switches off. |
| A skin that stops working when a rank expires | Grant only the node, leave `hide-without-permission: true`. The armour keeps the id and the look returns the day the rank does. |

<Callout type="tip" title="consume-skin-item decides whether a skin is single-use">
With `consume-skin-item: true` — the default — applying eats the item, so a skin is a consumable.
Turn it off and one item skins an unlimited number of pieces.
</Callout>
